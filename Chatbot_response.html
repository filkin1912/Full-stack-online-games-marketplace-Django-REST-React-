2 Is it RAG?

No — this is not RAG.

Classic RAG = retrieve relevant chunks (embeddings + vector DB) → inject only those into the prompt.

What this project has instead:

User message → Load ALL games from DB → Put entire list in one LLM prompt → Answer

That is sometimes called “context stuffing” or in-context retrieval, not RAG.

Implications

  • Works for a small catalog (tens / low hundreds of games).
  • Does not scale well if the catalog grows huge (token limits, cost, latency).
  • No semantic “find similar games” layer — the model filters from the full list in the prompt.
There is also a rule-based fallback (fallback_recommendation) when AI_API_KEY is missing: regex on budget/genre, filter/sort in Python, no LLM.

3 Does it keep conversation context?

A) Frontend (React) — UI chat only

frontend_app/src/components/Chatbot/Chatbot.jsx keeps messages[] in component state:

  • Greeting when logged in.
  • Each user/bot turn appended locally.
  • Lost on page refresh (not persisted to DB or localStorage).
  • Not sent back to the server as history — only the latest message is POSTed.

B) Backend — no multi-turn LLM context

Each POST /api/chatbot/ call builds a fresh OpenRouter payload with:

  1. System prompt (formatting rules for recommendations).
  2. One user block containing: user email, preference memory (text), current message, full game_data list.

There are no prior assistant / user messages from earlier turns in that API call.

The model does not “remember” what you said two messages ago, unless that fact was saved as a preference or you repeat it.

C) ChatMemory — preference memory, not chat log

FieldPurpose
userFK to AppUser
keye.g. budget, preferred_genre
valuee.g. 50, Action
created_attimestamp

How preferences are saved

detect_and_save_preferences() in chatbot/services.py:

  • Regex detects budget in the user message → save_memory(user, "budget", ...).
  • If message contains genre words → save_memory(user, "preferred_genre", ...).
Each save_memory creates a new row — it does not update the old one. load_memory loads all rows and prints key: value lines, so duplicates are possible over time.

When memory is cleared

  • POST /api/chatbot/clear/ deletes all ChatMemory for that user.
  • Called from frontend on logout (AuthContext.onLogout).

RAG sits between ask_llm and both data stores: PostgreSQL catalog + external APIs → vector index → only relevant chunks go to the LLM.

Where RAG fits

  • Today: ask_llm receives the entire GameModel list (context stuffing).
  • With RAG: user message → embed query → retrieve top-k from vector index (DB catalog + synced external docs) → LLM prompt gets only those chunks + still can list DB games for price/stock.
  • External knowledge: when PostgreSQL has no genre/release/trend data, ingest pipeline pulls from APIs/feeds, chunks, embeds, and retrieves at answer time.

8 Strengths and limits

Strengths

  • Simple to understand and deploy.
  • Personalized-ish via stored budget/genre.
  • Safe fallback without API key.
  • JWT-protected endpoints.

Limits

  • Not RAG — no semantic search.
  • No true chat memory for LLM.
  • UI history is local only.
  • Preference rows can accumulate.
  • Cost/latency grows with catalog size.
  • FastAPI path not wired to real logic.

10 Bottom line

The chatbot is a JWT-backed game recommender using OpenRouter + GPT-4o-mini, with full-catalog prompt context (not RAG), light preference memory in PostgreSQL, and UI-only chat history on the frontend — not full conversational context in the LLM.
